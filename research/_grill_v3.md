### Q1 — "เปลี่ยนสิ่งที่ประเมิน" นี่คือเปลี่ยนโจทย์ชีววิทยาจริง หรือเปลี่ยนคำเรียกผลลัพธ์?
**สถานะ:** ✅ **ตอบแล้ว — "เปลี่ยนจริง"**
**ผลที่ล็อกทันที:** `research/subculture_criteria.md` **ตกรุ่น ใช้ต่อไม่ได้** · threshold coverage 0.35-0.70 + ข้อถกเรื่อง gap 0.70-0.80 ใน `audit_report.md` **ไร้ความหมายแล้ว** · ต้องหาเกณฑ์ "พร้อมอนุบาล" ใหม่ทั้งชุดจาก literature

**ทำไมข้อนี้มาก่อน:** สองสถานะนี้ไม่ใช่แค่ threshold คนละชุด แต่ **ทิศทางของสัญญาณอาจกลับด้านกัน**
- *พร้อม sub-culture* = ต้นแน่นขวด แตกกอเยอะ เบียดกัน → coverage **สูง** = ถึงเวลาตัดแยก
- *พร้อมอนุบาล* = ต้นเดี่ยวสมบูรณ์ **มีรากดี** ลำต้นแข็งแรง พร้อมออกไปเจอโลกจริง → มักเป็นคนละ stage คนละสูตรอาหาร (rooting medium) และ coverage สูงเกินอาจแปลว่า **แย่** (แย่งกัน/hyperhydricity) ไม่ใช่ดี

ถ้าเป็นการเปลี่ยนโจทย์จริง → `subculture_criteria.md` ใช้ต่อไม่ได้ ต้องหาเกณฑ์ใหม่จาก literature ทั้งชุด
ถ้าเป็นแค่เปลี่ยนคำเรียกให้เข้ากับบูธ → ของเดิมใช้ต่อได้เกือบหมด งานเหลือแค่ UI + wording

**คำตอบที่แนะนำ:** *เปลี่ยนโจทย์จริง* — เพราะถ้าแค่เปลี่ยนป้ายแต่เบื้องหลังยังคิดแบบ sub-culture ระบบจะให้คำตอบที่ผิดทิศ และคนในแล็บที่มาดูบูธจะจับได้ทันที

### Q2 — "ราก" จะเป็น feature หลักของระบบ หรือยอมรับตั้งแต่ต้นว่าประเมินจากส่วนเหนือวุ้นเท่านั้น?
**สถานะ:** 🟡 **ตอบครึ่งหนึ่งด้วยหลักฐานภาพจริงแล้ว (2026-07-29) — รอผล spike ยืนยันอีกครึ่ง**

#### 📸 หลักฐานใหม่: เปิดภาพขวดจริงดูแล้ว — **เห็นรากชัดเจน**
ภาพที่ตรวจ (พบที่ `C:\Users\User\Downloads\Mobile Devices\`):
`20260518_184506.jpg` · `20260518_184533.jpg` · `20260522_124107.jpg`

สิ่งที่เห็น:
- **วุ้นเป็นเจลใส ไม่ทึบ** → รากไม่ได้ถูกบัง มองทะลุเข้าไปได้
- **รากขาว/ครีม เลื้อยเป็นร่างแหชัดเจน** บริเวณก้นขวด เห็นผ่านกระจกได้ด้วยตาเปล่า
- เห็นเปลือกเมล็ด ไฮโปคอทิล ใบจริง แยกกันได้ชัด
- ขวดวางตะแคง มีหลายขวดในเฟรม (พื้นหลังเป็นขวดอื่นเบลอ)

**→ สมมติฐาน "รากจมวุ้นมองไม่เห็น" ที่กลัวกันไว้ ไม่จริงสำหรับขวดชุดนี้**

⚠️ **แต่ยังสรุปไม่ได้ 2 เรื่อง:**
1. **ตาคนเห็น ≠ โมเดล segment ได้** — รากบางและโปร่งแสง เป็นเคสที่ segmentation พลาดง่าย → ต้องรอผล spike
2. ขวดชุดนี้เป็น**ต้นกล้าเล็ก วุ้นใส ความหนาแน่นต่ำ** — culture ที่แน่นกว่าหรือวุ้นขุ่นกว่าอาจต่างไปโดยสิ้นเชิง

📌 **ผลพลอยได้:** ต้นในภาพ **น่าจะเป็นพริก (Capsicum)** จากรูปใบและช่วงเวลา (พ.ค. 2026 = ชุดเพาะเมล็ดของ v1) — ถ้าใช่ ข้อค้าง "ไม่รู้ชนิดพืช" คลายลงบางส่วนสำหรับภาพชุดนี้ **รอเจ้าของโครงการยืนยัน**

**ทำไมข้อนี้อาจล้มโปรเจกต์:** ตัวชี้วัดความพร้อมอนุบาลอันดับหนึ่งคือ **ระบบราก** (จำนวน/ความยาว/ราก
ฝอย) — ถ้ามองไม่เห็น ระบบจะประเมินสิ่งที่สำคัญที่สุดไม่ได้เลย
*(หมายเหตุ: ข้ออ้างชีววิทยาในหัวข้อนี้ยังไม่ผ่าน citation gate — ต้องให้ `vitro-researcher` verify ก่อนใช้อ้างอิงจริง)*

**สิ่งที่ยังไม่มีใครเช็ค:** spike test 2026-07-05 ทดสอบแค่ prompt `plant` / `leaf` — **ไม่เคยลอง prompt `root` เลยสักครั้ง** และภาพที่มีเป็นมุมที่ไม่ได้ตั้งใจถ่ายราก

**ข้อสังเกตที่อาจพลิกเกม:** ในขวดวุ้น รากมักเลื้อยไปตามผนังขวดและ**มองเห็นได้จากมุมข้าง** ถ้าจริง = รากไม่ใช่ปัญหา แต่เป็นจุดขายของระบบเลย

**ทางเลือกสำรองที่แข็งแรงกว่าที่คิด:** **hyperhydricity (ใบแก้ว/vitrification)** เป็นสาเหตุใหญ่ที่ทำให้อนุบาลไม่รอด และเป็นความผิดปกติที่ **"เห็นด้วยตา"** ชัดมาก (ใบใส ฉ่ำน้ำ หนาผิดปกติ) → เป็น feature ที่กล้องจับได้ดีและเล่าหน้าบูธได้สวย

**คำตอบที่แนะนำ:** *อย่าเพิ่งเลือก — ยิง spike test เหมือนที่เคยช่วยชีวิตโปรเจกต์เมื่อ 07-05* ถ่ายขวดจริงมุมข้าง แล้วรัน SAM3 PCS prompt `root` / `roots`
พร้อม **kill criterion ล่วงหน้า:** ถ้าเจอรากได้ไม่เกินครึ่งของภาพที่ทดสอบ หรือ conf ต่ำกว่าที่ `plant`/`leaf` ทำได้อย่างชัดเจน → **ตัดรากทิ้งทันที ห้ามดันต่อ** แล้วย้ายแกนไป hyperhydricity + ลักษณะยอด/ใบ พร้อมเปลี่ยนคำเรียกผลลัพธ์ให้ซื่อสัตย์ว่าเป็นการคัดกรองเบื้องต้น ไม่ใช่คำตัดสิน

**🚧 spike ติด blocker (2026-07-29) — ยังไม่มีผล:** `vitro-fullstack` ทำ recon แล้วรายงานตรงๆ ว่า **ยิงไม่ได้เพราะไม่มี Roboflow API key** — ไม่มี env var `ROBOFLOW_API_KEY`, ไม่มีไฟล์ config, ที่เจอใน `src/android/app/build.gradle.kts` เป็น placeholder `"YOUR_API_KEY_HERE"` ไม่ใช่คีย์จริง และ MCP server ต้องให้เจ้าของโครงการทำ OAuth เอง **ยังไม่ได้ยิงภาพใดๆ ทั้งสิ้น ไม่มีผลให้รายงาน** (agent ยืนยันแล้วว่าภาพทั้ง 3 ไฟล์มีจริง และ `inference-sdk` ติดตั้งใน env `ml` จริง — พร้อมยิงทันทีที่ได้ credential)

**🚀 บรีฟ spike ที่ส่งไป (2026-07-29):** มอบ `vitro-fullstack` รัน SAM3 PCS prompt `root`/`roots`/`plant root`/`white root` + `leaf` เป็น baseline ควบคุมในภาพเดียวกัน บนภาพจริงทั้ง 3 ไฟล์ · kill criterion ตรึงไว้ล่วงหน้าแล้ว: **ต้องเจอรากใน ≥2 จาก 3 ภาพ + mask ต้องทับรากจริง (ตรวจด้วยตาจาก overlay ไม่ใช่ดูแค่ confidence)**

## 📐 ประเมิน feature / parameter (ตอบคำสั่ง 2026-07-29)

### หลักการที่ใช้ตัด
1. **น้อยแต่อธิบายได้ ชนะ เยอะแต่คลุมเครือ** — หน้าบูธต้องตอบได้ใน 1 ประโยคว่า "ทำไมขวดนี้ได้ผลนี้"
2. **ไม่มี label จากแล็บ** → ทุก threshold คือการเดาที่มีเหตุผล ยิ่งมี knob เยอะ ยิ่งเดาเยอะ ยิ่งพัง
3. ตัดทุก feature ที่ต้อง **calibrate หน่วยจริง** ทิ้ง (ดูของที่ตัดออกด้านล่าง)

### ✅ feature ที่เสนอให้ใช้ — 4 ตัวตัดสิน + 2 safeguard

| # | feature | คำนวณจาก | ทำไมต้องมี |
|---|---|---|---|
| 1 | `root_ratio` | area(mask `root`) / area(mask `plant`) | ตัวชี้วัดอันดับ 1 ของความพร้อมอนุบาล — **ทั้งหมดขึ้นกับผล spike** |
| 2 | `leaf_count` | จำนวน instance mask `leaf` ที่ conf ≥ 0.5 | ตัวแทนความสมบูรณ์ของยอด · พิสูจน์แล้วว่าทำได้ (17 ใบ conf 0.57-0.91) |
| 3 | `greenness` | ค่าเฉลี่ย G / hue ในพื้นที่ mask ใบ | ตัวแทนคลอโรฟิลล์/ความแข็งแรง · ต้นซีด = ยังไม่พร้อมออกขวด |
| 4 | `hyperhydricity_index` | สัดส่วน pixel ใบที่ saturation ต่ำ + value สูง | จับ "ใบแก้ว" ที่ทำให้อนุบาลไม่รอด · **จุดขายหน้าบูธ** |
| S1 | `glare_score` | สัดส่วน pixel ที่ V>0.95 & S<0.2 ใน ROI | **ลด confidence เท่านั้น ห้ามใช้ตัดสินคลาส** |
| S2 | `mean_confidence` | ค่าเฉลี่ย conf ของ mask ที่ใช้ | ถ้า segment ไม่ดี ต้องบอกผู้ใช้ ไม่ใช่เดา |

### ❌ ของที่ตัดออก (ตัดเพราะเหตุผล ไม่ใช่เพราะลืม)
- **`coverage_ratio`** — มรดกจาก v2 และ **ความหมายกลับทิศแล้ว** (แน่นขวด = ดีสำหรับ subculture แต่อาจ = แย่สำหรับอนุบาล) เก็บไว้แสดงเป็นข้อมูลได้ แต่**ห้ามใส่ในสูตรตัดสิน** จนกว่าจะรู้ทิศจริง
- **`height_cm` / `width_cm`** — ใน `vitrovison_cascade_api.ipynb` คำนวณจาก `PIXEL_TO_CM = 0.1 # placeholder` = **ตัวเลขปลอม** ถ้าจะใช้ความสูงต้องเป็น ratio เทียบ ROI เท่านั้น ห้ามโชว์หน่วย ซม. จนกว่าจะมี scale reference จริงในเฟรม
- **`shoot_count`** — ซ้ำซ้อนกับ `leaf_count` ในต้นกล้าเล็ก และแยกยอดจากก้านผ่านกระจกยาก

### 🔢 สรุปตัวเลข
- **feature ที่วัด: 6 ตัว** (4 ตัดสิน + 2 safeguard)
- **threshold ที่ต้องตั้ง: 4 ตัว** (ตัวละ 1 เกณฑ์ สำหรับ feature ตัดสิน)
- **threshold safeguard: 2 ตัว**
- **รวมตัวเลขที่ต้องอธิบายได้: 6 ตัว**

### 🎯 ข้อเสนอสำคัญ: ใช้ rule-based แบบ hard threshold **ไม่ใช่ weighted score**
weighted score ต้องตั้งน้ำหนักเพิ่มอีก 4 ตัว = 10 ตัวเลขที่ไม่มี label มารองรับ และเวลามีคนถามหน้าบูธว่า "ทำไมได้ 0.62" จะตอบไม่ได้
hard threshold ตอบได้ทันที: *"ขวดนี้ยังไม่พร้อมเพราะยังไม่มีราก"* — เข้าใจทันที ตรวจสอบได้ และถ้าผิดก็เห็นชัดว่าผิดตรงไหน

### Q3 — 🚨 marketplace **แทนที่** VitroVision หรือ **ครอบ** VitroVision ไว้ข้างใน?
**สถานะ:** ✅ **ตอบแล้ว — "ครอบไว้ข้างใน" (ตรงกับที่แนะนำ)**

> คำตอบเจ้าของโครงการ: *"เป็นแค่แนวคิดไว้สำหรับ product ที่จะ launch VitroVision เพื่อให้คนในแล็บสามารถใช้บอกความพร้อมของพืชที่จะส่งให้เกษตรกรได้"*

**ล็อกแล้ว:**
- **ของที่สร้างรอบนี้ = เครื่องมือสำหรับ "คนในแล็บ"** ใช้ประเมิน/บอกความพร้อมของพืชที่จะส่งให้เกษตรกร
- **ผู้ใช้หลัก = เจ้าหน้าที่แล็บ** ไม่ใช่เกษตรกร ไม่ใช่ผู้ซื้อทั่วไป
- **marketplace = vision ปลายทาง ไม่ใช่ scope รอบนี้** — ห้ามเริ่มสร้าง auth 2 บทบาท / listing / order / chat / review
- งาน CV ทั้งหมดวันนี้ **ยังใช้ได้ครบ** · spike รากที่รันอยู่ยังมีค่า
- 🎤 **ใช้เป็นเรื่องเล่าหน้าบูธ:** ไม่ใช่ "AI วัดพืช" แต่คือ *"แล็บบอกเกษตรกรได้ว่าต้นพร้อมส่งจริง"*

**บรีฟใหม่ (2026-07-29):** อยากได้ web app แบบ **Fastwork** แต่เปลี่ยนสองฝั่งเป็น
- ฝั่งผู้ให้บริการ = **แล็บเพาะเลี้ยงเนื้อเยื่อ**
- ฝั่งผู้ใช้ = **คนที่จะมาเลือกหาพืชจากแล็บไปปลูก + สั่งให้แล็บเพาะพืชให้ได้**

**ทำไมนี่ไม่ใช่การปรับทิศแต่เป็นคนละผลิตภัณฑ์:** ของเดิมคือ **เครื่องมือวัด** (CV มองพืชในขวด) · ของใหม่คือ **แพลตฟอร์มตลาดสองฝั่ง** (บัญชีผู้ใช้ 2 ประเภท, ประกาศขาย, ค้นหา/กรอง, สั่งงาน, แชท, สถานะออเดอร์, รีวิว) — คนละ domain คนละ skill set แทบไม่มีโค้ดเดิมใช้ต่อได้

**⚠️ pivot ที่ 3 ของวันนี้** (YSC→exhibition · Android→web+อนุบาล · CV→marketplace) และ **บทเรียนข้อ 6 ที่โปรเจกต์บันทึกไว้เองจากความล้มเหลวของ v1 คือ "เปลี่ยนสถาปัตยกรรมไปเรื่อยจนไม่เข้าใจงานตัวเอง"** — ต้องหยุดถามให้ชัดก่อนลงมือ ไม่ใช่เพราะบรีฟไม่ดี แต่เพราะราคาของการเดาผิดรอบนี้สูงมาก

**คำตอบที่แนะนำ: *ครอบไว้ข้างใน* — marketplace เป็นเปลือก, VitroVision CV เป็นแกนที่ทำให้มันไม่ใช่ Fastwork ธรรมดา**
เหตุผล 3 ชั้น:
1. **ถ้าไม่มี CV โปรเจกต์นี้ไม่เหลืออะไรเป็นของตัวเอง** — marketplace เปล่าๆ คือ CRUD ที่ใครก็ทำได้ ไม่มีอะไรให้เล่าหน้าบูธงานวิทยาศาสตร์
2. **CV กลายเป็น "ชั้นความน่าเชื่อถือ" ที่แก้ปัญหาจริงของตลาดนี้พอดี** — คนซื้อพืชในขวดออนไลน์ไม่มีทางรู้ว่าต้นในขวดสมบูรณ์พอจะรอดหลังออกขวดไหม → แล็บอัปโหลดรูปขวด → AI ประเมิน **"ความพร้อมอนุบาล"** ติดไปกับประกาศขาย = ผู้ซื้อเห็นหลักฐาน ไม่ใช่แค่คำโฆษณา **นี่คือจุดที่งานทั้งหมดที่ทำมาเสียบเข้าล็อกพอดี**
3. งานที่ทำไปแล้ววันนี้ (spike ราก, 6 feature, hard threshold) **ยังใช้ได้ทั้งหมด** ถ้าเลือกทางนี้ · ถ้าเลือก "แทนที่" → spike ที่กำลังรันอยู่กลายเป็นงานเสียเปล่าทันที

**ถ้าเลือก "แทนที่" ต้องยอมรับสิ่งเหล่านี้:** ทิ้งงาน CV ทั้งหมดตั้งแต่ ก.ค. · ต้องสร้าง auth 2 บทบาท + listing + search + order + chat + review ตั้งแต่ศูนย์ · ไม่มีข้อมูลแล็บจริงสักแห่งในระบบ · และต้องตอบให้ได้ว่าของที่ได้ต่างจาก Fastwork/Shopee ตรงไหน
*(ไม่ได้เลือกทางนี้ — เก็บไว้เป็นบันทึกว่าเคยพิจารณาแล้ว)*

### Q4 — แล็บส่งอะไรให้เกษตรกร: **ต้นในขวด** หรือ **ต้นที่อนุบาลเสร็จแล้ว**?
**สถานะ:** ⏳ รอคำตอบ

**ทำไมข้อนี้เปลี่ยนทุกอย่าง:** คำว่า "พร้อมส่งให้เกษตรกร" แปลได้ 2 แบบที่ต้องการ feature คนละชุดโดยสิ้นเชิง

| | A. ส่งเป็น **ขวด** (เกษตรกรอนุบาลเอง) | B. ส่งเป็น **ต้นกล้าที่อนุบาลแล้ว** (แล็บอนุบาลเอง) |
|---|---|---|
| "พร้อม" แปลว่า | ต้นในขวดแข็งแรงพอจะรอดตอนออกจากขวด = **acclimatization readiness** | ต้นผ่านการอนุบาลแล้ว รอดจริง แข็งแรงพอลงแปลง |
| ถ่ายรูปอะไร | **ขวดแก้ว** — ผ่านกระจก + glare + ไอน้ำ | ต้นในถาดเพาะ/กระถาง — **ไม่มีกระจกขวางแล้ว** |
| feature ที่ใช้ | ราก + ใบ + greenness + hyperhydricity ✅ **ตรงกับที่ออกแบบไว้** | ความสูง จำนวนใบจริง สีใบ ความสมบูรณ์ — **ไม่ต้องใช้ SAM3 ทะลุกระจกเลย** |
| งานที่ทำมาทั้งหมด | ใช้ได้ครบ | **ครึ่งหนึ่งไม่ได้ใช้** (spike ทะลุกระจก, กฎห้าม automatic mode, cascade detect ขวด) |

**คำตอบที่แนะนำ: A (ส่งเป็นขวด)** เพราะ
1. งานทั้งหมดที่พิสูจน์มาแล้วตั้งแต่ 5 ก.ค. อยู่บนสมมติฐานนี้ — spike ทะลุกระจกที่ผ่านแล้วคือสินทรัพย์หลักของโปรเจกต์
2. โจทย์ยากกว่าและ**ไม่มีใครทำ** = มีอะไรให้เล่าหน้าบูธ · ถ้าเป็น B มันคือการถ่ายรูปต้นไม้ธรรมดาที่มีคนทำเยอะแล้ว
3. ตรงกับปัญหาต้นทางที่เจ้าของโครงการเจอเอง (พืชโตเต็มขวดแล้วไม่มีคนไปจัดการทัน)

**แต่ถ้าความจริงคือ B ต้องรู้ตอนนี้** — เพราะมันแปลว่าเลิกใช้ SAM3 ทะลุกระจกได้เลย และงานจะง่ายลงมาก (แต่ก็ธรรมดาลงมากด้วย)
